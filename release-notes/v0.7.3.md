# v0.7.3：修复 DSH NEXT 2.0.19 上的成员派发与子会话可读性

发布日期：2026-10-18

## 问题

DSH Desktop NEXT `2.0.19-next` 内置的宿主版本是 `0.2.1-rc.2`。在这个宿主上建队、批准、派任务都正常，但成员一启动就失败，日志里是两句话：

```text
agent-teams: member dispatch failed for verifier: Error: agent-teams: provider "spawn" cannot apply a member persona
tool-session-query: ... session "eb3c1b69-..." contains event type "agent-teams/member-composition" (seq 4)
unknown to this harness and not marked ignorable; refusing to interpret the log
```

两个问题彼此独立：

1. **宿主不再声明 persona / toolFilter 能力。** `@deepseek-ai/dsh-subagent-spawn-in-process` 的 capabilities 固定为 `agentOptions` / `agentPreset` / `outputSchema` / `depthLimit`，`SubagentStartRequest` 也没有 `persona` / `toolFilter` 字段 —— 成员人设与工具限制改由宿主预设（agent preset）负责，启动请求根本不接受这两项。旧代码按「宿主支持 persona」直接发起派发，于是被能力检查拒绝，成员一个也起不来。
2. **插件往会话里写宿主不认识的会话事件。** 旧代码用 `session.append('agent-teams/member-composition', ...)` 存组合快照；`0.2.1-rc.2` 的事件目录里没有这个类型，事件也没标 `ignorable`，于是**该子会话从此不可读**（`SessionFormatUnsupportedError`），后续 `send_message` / 交付一律报 `subagent "..." is unavailable`。这不是显示层问题：日志本身被拒绝解释。

## 修复

- **preset-only 宿主走组合安装路径。** 能力位里没有 `persona` / `toolFilter`、但有 `agentPreset` 且宿主提供 `startActivation` 时，不再把它们塞进启动请求，改为在成员子上下文里自行安装：
  - `childCtx.tools.restrict(toolFilter)` 限制可用工具；
  - `childCtx.systemPrompt.section({ name: 'deployment:persona-prefix', order: DEPLOYMENT_PERSONA_PREFIX, text: persona })` 写入成员人设。
  宿主原生支持这两项能力的老版本仍走原路径，行为不变。
- **`team.json` 成为冷恢复的唯一权威。** 宿主的 continuable descriptor 在启动路径上不保存 persona / toolFilter，所以现在**每个成员**都把生效的 `toolFilter` 记进 `team.json`；冷恢复时从这份持久记录重建人设与过滤，并在成员第一个请求之前安装。没有过滤记录的成员**拒绝恢复**（`has no durable composition snapshot`），不会以「无限制工具」的形态偷跑；`tools.restrict` 失败同样中止派发。
- **不再写任何自定义会话事件。** 删除 `agent-teams/member-composition` 的写入与 `SessionEventMap` 增强，组合状态只存在于插件自己的持久记录里。宿主日志保持可读。
- **兼容矩阵收录 `0.2.1-rc.2`。** `compatibility.json` 增加该宿主（`track: preview`），21 条 `@deepseek-ai/dsh-*` peer 白名单同步枚举；推荐宿主仍是 `0.2.0-rc.2`，未提升任何版本的支持等级。

## 回归覆盖

- 新增 `scripts/member-composition.test.mjs`（4 个用例，已挂进 `verify:harness-contract`）：preset-only 宿主在首个请求前装好人设与精确过滤；`restrict` 失败必须中止派发而不是放行；冷恢复只从 `team.json` 重建且不追加会话事件；无过滤 / 损坏过滤的成员记录被拒，普通子代理不受影响。
- `harness-compat-tdd` 32/32、`member-failure-tdd` 三种矩阵各 10/10、`lifecycle-verify` 的 `--activation-harness` / `--modern-harness` / `--delivery-harness` 全部通过；`quality-gates`、`stability`、`lineage`、`tool-policies`、`capabilities` 等既有脚本照常执行。
- 本机宿主 `0.2.1-rc.2`（DSH NEXT 2.0.19）的实际日志是本版本两个缺陷的原始证据；修复后同一宿主上类型检查、构建与上述回归全部通过。需要说明的是：`capabilities.test.mjs` 中依赖真实子进程（PTC `run_code`、`spawnSync`）的用例在被沙箱限制子进程的环境里会以 `EPERM` 失败，这与本版本改动无关，在无限制环境或 CI 中应全绿。

## 已知遗留

- **已被 0.7.2 写坏的子会话无法由本插件修复。** 那些会话的日志里已经有宿主不认识的 `agent-teams/member-composition` 事件，拒绝发生在插件加载之前的会话读取路径。可行做法是不要再向这些成员发消息，直接归档团队并重建；插件不会静默删除或改写用户的历史会话。

## 升级

```sh
dsh plugin --profile <profile> add dsh-agent-teams-fish@0.7.3
```

升级后重启 DSH。已存在的 `team.json` 无需迁移：成员缺少 `toolFilter` 记录时，冷恢复会明确拒绝并在派发前报错，而不是降级放行；重新派发一次即可写入新的持久组合。
